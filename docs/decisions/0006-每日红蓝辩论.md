# 0006 每日红蓝辩论：机器人主持，试行一周

- 状态：已采纳（试行 7 场）
- 日期：2026-10-27
- 记录者：PCClaude
- 相关：#26，`docs/debates/README.md`，`tools/debate.mjs`

## 背景

房主希望全体 Agent 每天针对隔壁做一次红蓝辩论：1 名红方挖缺陷、主张停止推进，2 名蓝方反驳，2 名裁判判胜负并留下对开发有用的观点。

限制和 0001、0004 一样：Agent 之间不能直接对话，不会主动看 GitHub，不记得上一次会话；有的跑在云端，有的跑在房主的电脑上，醒来的时间不一样。所以辩论只能异步进行，靠 GitHub 上的标签叫人。

房主定了三件事（#26）：先试行一周；每天 10 点开场，用洛杉矶时区；红方赢了不直接停项目，论点被判成立并且关系到项目方向时打 `needs-human`，由房主决定。

## 选项

1. **每个 Agent 按一张固定排班表自觉发言**：不用写代码，但没人推进轮次。谁没醒，整场就卡住；超时、排班变化都要人去协调。
2. **房主每天开场、点名**：最简单，但房主成了每天的瓶颈，和 0001 的原则冲突。
3. **工作流里的机器人主持**：定时开场，按登记表排班，用 `handoff:` 标签叫人，超时跳过，自动汇总。Agent 端只靠已有的轮询（0004），不用改。

## 决定

选 3。要点：

- **状态不另存**：角色写在 issue 正文的隐藏注释里，轮次每次都从评论重放出来。机器人重复运行、漏跑一次都不会出错，也不需要数据库或提交文件。
- **排班按历史次数**：红方挑当红方最少的，裁判挑当裁判最少的两人，次数相同优先一家一个（按登记表的“工具”列分 Claude 和 GPT），剩下的当蓝方。登记表变了自动适应；少于 3 个 Agent 不开场。
- **每轮 3 小时，超时跳过**：红方没立论就流局；裁判同时接手，避免后判的人被先判的带着走（“先写完再看对方”只能靠自觉）。
- **两位裁判不一致就是平局**，不设第三票。
- **证据只认三种**：文件和行号、公开链接、能复现的操作。其余标「假设」。这是为了防止 Agent 编造“经验”和数据。
- **产出要能落地**：每位裁判最多开 1 个 `from-debate` issue；关系到项目方向的，打 `needs-human`。
- **先办 7 场**，办满后自动开一个评估 issue，打 `needs-human`，由房主决定继续、减频还是停止。频率是房主的事，因为它直接决定房主要付多少 token，其中 3 个 Agent 还跑在房主自己的电脑上。

## 影响

- 每个 Agent 不需要额外设置：辩论 issue 会出现在 `board.mjs` 的“指派给你的 issue”里。但定时检查是 30 分钟一次时，每轮 3 小时足够；改成更低频的话，轮次时限也要跟着放长。
- **和 0005（分阶段轮询）的关系**：
  - 0005 用“最近 72 小时有没有活动”判断休眠，辩论 issue 上的评论和机器人动作**不算活动**，否则天天有辩论，项目永远进不了休眠。`board.mjs` 的 `QUIET_LABELS` 已经排除了 `debate` 和 `debate-eval`。
  - 两边认同一个暂停开关：有开着的 issue 带 `project:paused` 时，board 停止自动检查，辩论机器人也不开新的一场。
  - **已知冲突**：项目休眠时，只能定时唤醒模型的 Agent 会降到每 6 小时到每天检查一次，比每轮 3 小时的时限慢，这时开的辩论大多会超时流局。试行这一周项目是活跃的，碰不到；如果继续办，要么休眠时不开场，要么拉长时限。
- 定时工作流每小时跑一次（只在默认分支上运行），公开仓库不占 Actions 额度。
- **什么时候重新考虑**：评估 issue 显示 `from-debate` 的 issue 很少被做，或者超时很多（说明 Agent 醒得不够勤），就减频或者停掉；论点开始重复，就换主题表或者拉长间隔。
