# 0005 分阶段轮询：活跃、休眠、暂停

- 状态：已采纳
- 日期：2026-10-27
- 记录者：PCClaude
- 相关：#21（MacGPT 提出，房主授权），#17/#18（本机唤醒器），0004，`AGENTS.md`「自动接力」，`docs/agents/polling.md`

## 背景

项目会开发一阵、停一阵。0004 要求所有 Agent 每 20～30 分钟检查一次待办。项目停下来的时候，仍然每 30 分钟叫醒一次模型是浪费；而房主希望不用逐个给 Agent 发提示词，规则写在仓库里，Agent 轮询时自己读到。

事实：
- 先跑脚本、有待办才叫醒模型的环境，空检查不花 token，只占一点 GitHub 接口额度（每次几个请求，远低于限额），降频没有收益。
- 只能定时叫醒模型的环境，每次醒来都花 token，空检查的代价是真实的。
- 路由机器人、CI 每次都会在 PR 上留评论和标签，所以“PR 最近有更新”不能当作有人在工作。
- 所有 Agent 和房主共用一个 GitHub 账号，机器人的操作是另一个账号 `github-actions[bot]`，可以区分。

## 选项

1. 在仓库里写一个“状态文件”，由某个 Agent 维护。要有人提交才能改，房主没法随手暂停，也容易和实际情况不一致。
2. 每个 Agent 各自按文字规则判断。写法有出入，每个 Agent 判断得不一样。
3. 由 `tools/board.mjs` 根据 GitHub 上的事实算出模式，所有 Agent 读同一个结果。房主暂停用一个标签，网页或手机上点一下就行。

## 决定

选 3。模式由 `board.mjs` 计算（`node tools/board.mjs <名字> --status` 查看，`--quiet` 和普通模式的第一行也带 `mode=…`）：

| 模式 | 怎么判定 | 检查频率 |
| --- | --- | --- |
| 暂停 `paused` | 有打着 `project:paused` 标签的开放 issue（固定的“暂停开关” issue） | 不再叫醒模型：`--quiet` 一律退出 0，手动运行仍会列出待办。**定时任务不删**，脚本照旧跑，所以撤销标签后自动恢复 |
| 休眠 `dormant` | 最近 72 小时，仓库里没有人提交、评论、评审、开关 issue/PR、改标签。**机器人（`github-actions[bot]`）的事件不算**，点星标之类也不算；**每日辩论 issue（`debate`、`debate-eval` 标签）上的发言和标签变化也不算**，否则每天都是活跃 | 能用脚本过滤的环境：脚本照常每 30 分钟跑（不花 token）；只能定时唤醒模型的环境：每天一次 |
| 活跃 `active` | 其他 | 每 30 分钟 |

要点：
- **待办是“现在还有什么”，不是“新发生了什么”。** 休眠中遗留的交接不会丢，醒来第一次检查就能看到，输出里会标出放了几天。因此不需要单独的“恢复后补查”。
- **只能定时唤醒模型的环境靠自己调整。** 醒来运行 `board.mjs <名字> --next-check`（活跃 30，休眠或暂停 1440），和自己现在的定时间隔比较，不一样就改定时。能不能改自己的定时因工具而异，写进 `capabilities.md`；改不了就保持 30 分钟并如实记录这项浪费。降到每天一次后，恢复最长晚一天发现，要马上处理用 `review-now`。（MacGPT 评审 #24 时指出：最初的文档只说“降频”，没有写谁来改、怎么改。）
- **脚本不降频。** 休眠节省的是模型唤醒，不是脚本运行。能脚本过滤的环境不用重新配计划任务。
- 活动判断翻页读事件（最多 3 页、300 条），直到找到有效活动、翻过 72 小时或没有更多数据；翻到上限仍没有结论就按活跃处理，不静默判休眠（MacGPT 第二轮评审指出：最近 100 条全是辩论事件会误判休眠）。
- 评论、PR 和 issue 列表翻页读到最后一页，评论超过 100 条也不会漏掉新反馈。
- 休眠时，同一批没处理的待办不要每次都重新叫醒模型：本机唤醒器在休眠模式下，同一批待办最少隔 6 小时才再启动一次（活跃时 30 分钟），并读取 board 输出第一行的 `mode=`。
- **恢复**：房主一动（提交、评论、改标签，包括撤掉 `project:paused`）就是活动，下一次检查进入活跃；最长等一个脚本周期（30 分钟）。要马上处理，用 `review-now`。
- **退出码**：0 没事，10 有待办，20 出错（原因在标准错误）。出错的处理：本地日志，指数退避；连续失败也不要往 GitHub 上刷评论（`gh` 本身就坏了的时候也评论不出去），由房主在 Agent 报告里看到。
- **作者自己 PR 的反馈**：`board` 额外检查“我的 PR 上，有别人在我最后一次发言之后留了新评论”，因为只留评论、不改标签的情况之前看不到。约定仍然是：需要对方回应的评论，同时改 `handoff` 标签。
- **各环境的实际能力**（能不能脚本唤醒、订阅能不能叫醒、最短周期）不在这里假设，由各 Agent 在自己的环境验证后，写进 [`docs/agents/capabilities.md`](../agents/capabilities.md) 里自己的那一行。不能脚本唤醒的如实写，用每天一次的兜底。

与 #21 提案的两处出入，写在这里让评审者检查：
1. #21 提议“休眠时每 6 小时检查”。我把它限定在“要花 token 的环境”，因为脚本过滤的环境降频没有收益；这类环境休眠默认每天一次，和 #21 一致（6 小时只留给本机唤醒器的重启间隔）。
2. 我曾想过让搁置超过 72 小时的 PR 不再触发唤醒。没有采纳：被指派的评审者离线几天回来后，恰恰需要被叫醒。改为只标注“放了几天”，靠 6 小时的重启间隔避免反复叫醒。

## 影响

- `tools/board.mjs` 增加模式判断、`--status`、新评论检查和明确的退出码；`tools/test-board.mjs` 覆盖各条路径。
- 本机唤醒器（`tools/dispatch.mjs`，#18 合并后）读取 `mode=`，休眠时把重复启动的最短间隔拉到 6 小时，另开 PR。
- 房主暂停：给 issue「暂停开关」打上 `project:paused`；恢复：去掉标签。
- 什么情况下重新考虑：GitHub 事件接口的延迟或保留期变化（现在只用最近 100 条事件，每分钟活跃的仓库会不够用，那时要换成按时间取）；或者出现能被 GitHub 事件直接唤醒的 Agent 环境（那时轮询可以整个取消）。
