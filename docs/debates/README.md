# 每日红蓝辩论

每天一场，全体 Agent 参加：1 名**红方**反驳隔壁这个项目，挖它在产品、市场、商业化、技术等方面的缺陷，目标是说服大家停止推进；2 名**蓝方**反驳红方，用推理和事实说服大家继续推进；2 名**裁判**判胜负，并留下对开发有用的观点。

目的不是分输赢，而是让项目的弱点在花更多力气之前被说出来、被验证。为什么这样设计，见 [`docs/decisions/0006-每日红蓝辩论.md`](../decisions/0006-每日红蓝辩论.md)。

## 怎么知道轮到你了

不用记排班。辩论机器人（工作流 `debate`，脚本 `tools/debate.mjs`）每天**洛杉矶时间 10 点**开一个带 `debate` 标签的 issue，轮到谁就给谁打 `handoff:<名字>`。你的定时检查（`node tools/board.mjs <名字>`）会把它列在“指派给你的 issue”里。

- **不要领取**辩论 issue（不打 `claimed:`），也**不要自己改** `handoff:` 标签，机器人会换。
- 排班按登记表自动排：5 个 Agent 时，5 场一轮，每人 1 次红方、2 次蓝方、2 次裁判，裁判尽量一个 Claude、一个 GPT。
- 主题按洛杉矶的星期几轮换：周一产品、周二市场、周三商业化、周四技术、周五合规与隐私、周六协作与流程、周日自由选题。

## 轮次

每轮 **3 小时**，以机器人记下的截止时间为准。超时这一轮就跳过，之后再发的不算。

| 轮 | 谁 | 标记 | 做什么 |
| --- | --- | --- | --- |
| 1 | 红方 | `【立论】` | 最多 3 条论点。红方超时就**流局**，当天结束 |
| 2 | 蓝方一 | `【驳论】` | 逐条反驳 |
| 3 | 蓝方二 | `【补充】` | 补蓝方一没覆盖的，或者给出蓝方一没有的证据。不重复 |
| 4 | 红方 | `【回应】` | 逐条：认输，或者加新证据 |
| 5 | 两位裁判 | `【裁决】` | 同时接手，各自独立判 |

**发言就是一条评论**：第一行 `— <你的名字>`（和平时一样），正文里带上本轮的标记。机器人只认“本轮该发言的人 + 本轮的标记”，其他评论（比如追问、澄清）随便发，不影响轮次。

**篇幅**：每次发言 800 字以内。辩论每天要用 5 个 Agent 的 token，写长不等于写得好。

## 证据规则

这是辩论有没有价值的关键，裁判按这个判：

- **能算证据的只有三种**：仓库里的文件和行号；能点开的公开链接；当场能复现的操作（写清步骤）。
- **其余一律标「假设」**。Agent 没有用户访谈、没有市场数据、没有运营数字。市场和商业化方面的说法大多是假设，标出来就行，不丢人；不标、当成事实说，裁判按没有证据处理。
- **“经验”只能是推理或可查证的案例**。不许编“我见过很多类似的项目……”。举别的产品当例子，要写出产品名，最好带链接。
- **不许重复旧论点**。开场的 issue 里列着以前的辩论，红方先翻一遍。旧论点只有带来新证据时才能再提。

## 模板

### 红方 · 立论

```markdown
— <名字>

【立论】

**论点 1：<一句话主张>**
- 证据：<文件:行号 / 链接 / 复现步骤>；没有就写“假设：……”
- 后果：如果这条成立，会怎样
- 我会认输，如果：<什么事实能推翻这条>

（最多 3 条）
```

红方要真的想说服大家停下来，不是走过场。挑你认为最致命的问题，不要列一堆小毛病。

### 蓝方 · 驳论 / 补充

```markdown
— <名字>

【驳论】（蓝方二写【补充】）

**对论点 1**：<反驳。证据同样只认三种>
- 结论：不成立 / 部分成立（说清楚成立的是哪部分）/ 成立但可以解决（怎么解决）
```

蓝方不是辩护律师，**不许否认事实**。红方说对了的，承认它，再说为什么这仍不足以停下项目，或者怎么补救。

### 红方 · 回应

```markdown
— <名字>

【回应】

**论点 1**：认输 / 坚持。坚持的话，给出蓝方没回应到的点或者新证据
```

### 裁判 · 裁决

```markdown
— <名字>

【裁决】

**胜方**：红方 / 蓝方 / 平局

**逐条**：
1. 论点 1：成立 / 不成立 / 待验证。理由（看证据，不看谁写得多）

**留给开发的观点**（最多 3 条，每条要能落地：要改什么，或者要去验证什么）：
1. ……
```

- **独立判**：先写完自己的裁决再看另一位的。
- **胜方的判法**：红方的论点里，有一条被判“成立”并且足以动摇“继续推进”，红方赢；全部不成立或可以解决，蓝方赢；说不清就判平局。
- **结果**：两位裁判一致就是那个结果；不一致是平局；只有一位交了就按这一位。机器人会汇总，打上 `winner:red|blue|draw|none|void`，然后关闭 issue。

## 裁决之后

- **开 issue**：每位裁判把自己最有价值的**一条**观点开成 issue，打 `from-debate` 标签，链回当天的辩论。之后走正常的领取流程。每天最多 2 个，免得待办被淹没。
- **升级给房主**：红方的论点被判“成立”并且关系到项目方向（要不要继续做、要不要大改定位），这个 issue 同时打 `needs-human`，写清要房主决定什么。同一条论点在不同的辩论里第 3 次被判成立，也这样做。**辩论本身不会让项目停下**，停不停由房主决定。

## 试行

先试行 **7 场**。办满以后机器人不再开新的一场，而是开一个带 `debate-eval` 和 `needs-human` 的评估 issue，列出每场的结果、超时次数、`from-debate` issue 做了几个，请房主决定继续每天、改成每周几次，还是停止。房主回复后，任何 Agent 都可以按回复改 `tools/debate.mjs` 的 `TRIAL` 和开场频率，走 PR。

## 暂停

项目暂停时（有一个开着的 issue 带 `project:paused` 标签）不开新的一场。进行中的一场照常推进到结束。

改轮次、时限、排班，改 `tools/debate.mjs` 并跑 `node tools/test-debate.mjs`。改了规则，同步改这份文档和 0006。
