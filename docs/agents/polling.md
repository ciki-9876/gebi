# 定期检查待办

Agent 不会主动看 GitHub，所以每个 Agent 要设一个**定期检查**。检查本身很便宜：一条命令，没事就什么也不做。频率跟着项目状态走，规则和理由见 [`0005-分阶段轮询`](../decisions/0005-分阶段轮询.md)。

```bash
node tools/board.mjs <你的名字>            # 看现在该做什么
node tools/board.mjs <你的名字> --status   # 只看项目现在是活跃、休眠还是暂停
```

有待办时按它列的顺序处理：先评审、再修改、再回复新评论、再合并，处理完再跑一遍。

PR 一打上 `ready-for-review`，评审者由工作流 `route` 自动指派，不需要作者或房主去通知。

## 项目状态和检查频率

| 状态 | 怎么判定（`board.mjs` 算，所有 Agent 读到的一样） | 能脚本过滤的环境 | 只能定时唤醒模型的环境 |
| --- | --- | --- | --- |
| 活跃 | 最近 72 小时有人（机器人不算）提交、评论、评审、开关 issue/PR、改标签。每日辩论 issue（`debate`、`debate-eval` 标签）上的发言不算 | 脚本每 30 分钟 | 每 30 分钟 |
| 休眠 | 连续 72 小时没有上面这些活动 | 脚本照旧每 30 分钟，不花 token | **每天一次**（1440 分钟） |
| 暂停 | 有开放的 issue 带 `project:paused` 标签（房主在固定的“暂停开关” issue 上打的） | 脚本照旧每 30 分钟，`--quiet` 一律退出 0 | **每天一次**（1440 分钟） |

“停止自动检查”的意思是**不再叫醒模型**，不是把定时任务删掉：脚本一直在跑，所以房主撤销标签后，下一次脚本检查（最长 30 分钟）自己就会发现，不需要任何人去重启。

- 休眠不会丢交接：board 列的是“现在还有什么”，醒来第一次检查就能看到休眠期间遗留的，并标出放了几天。评论和 PR 列表翻页读到最新一页，评论超过 100 条也不会漏掉新反馈。
- 恢复：房主一动（提交、评论、改标签，撤掉 `project:paused` 也算）就回到活跃。脚本过滤的环境最长等 30 分钟，只能唤醒模型的环境最长等一个已降频的间隔。要马上处理，用 [`review-now`](review-now.md)。
- 暂停和恢复都在 GitHub 网页或手机上点标签就行，不用提 PR。

### 只能定时唤醒模型的环境怎么自动降频、升频

这类环境（比如只能让模型按时间运行一段提示词的自动化）没有脚本过滤，每次醒来都花 token，所以要在模型醒来时**自己调整下一次的间隔**，不然不会降频：

1. **每次醒来都先运行** `node tools/board.mjs <名字> --next-check`，**即使没有待办也要运行**：输出一个数字才算有效，活跃 `30`，休眠或暂停 `1440`（分钟）。出错（退出码 20，或者没有数字）这一轮**不要改定时**，只记本地日志。
2. 数字有效且和你现在的定时间隔不一样，**就把定时改成这个数字**。你的工具能不能改自己的定时，要在 [`capabilities.md`](capabilities.md) 里如实写；不能改的，只能每次保持 30 分钟，并写明这一项浪费，由房主决定要不要手动改。
3. 再运行 `node tools/board.mjs <名字> --quiet`，退出码 10 才按待办处理。

**这类环境要用下面「模型定时版提示词」**，不要用后面的通用提示词：通用提示词在没有待办时立刻结束，永远不会运行第 1 步，也就不会降频。

延迟要说清楚：降到每天一次之后，房主恢复开发或撤销暂停，**最长要等一天**才会被发现。需要马上处理，用 [`review-now`](review-now.md)。脚本过滤的环境没有这个延迟。

## 先用脚本过滤，没事就不叫醒大模型

最省钱的做法：定时任务里**先跑脚本**，不要每次都让大模型读一遍上下文。

```bash
node tools/board.mjs <名字> --quiet
```

| 退出码 | 意思 | 怎么办 |
| --- | --- | --- |
| `0` | 没有待办（或者房主暂停了） | 什么也不做 |
| `10` | 有待办，已输出，第一行是 `mode=active` 或 `mode=dormant` | 叫醒 Agent 去处理 |
| `20` | 出错（`gh` 没登录、网络断了、接口限流），原因在标准错误 | 不叫醒 Agent；本地记日志，下次间隔拉长；**不要往 GitHub 上评论** |

你的工具如果能“运行脚本、根据退出码决定要不要触发会话”（系统 cron、任务计划程序、本机唤醒器，或各种自动化的“有输出才通知”选项），就用这个。只能每次都运行大模型提示词的环境，每次醒来都花 token，所以休眠和暂停时降到每天一次（见上节）；**别把“模型醒来后再运行脚本”说成零 token 空轮。**

各环境实际能不能脚本唤醒、订阅能不能叫醒自己、最短周期是多少，不要假设，验证后写进 [`capabilities.md`](capabilities.md) 里自己的那一行。

## 设置定时检查

你的工具有什么定时功能，就用什么。活跃时 30 分钟一次，不需要更快；休眠时按上表降频。

| 工具 | 怎么设 |
| --- | --- |
| Claude Code（云端会话） | 用定时任务（`create_trigger`，云端最短间隔通常是每小时），属于**只能定时唤醒模型**的环境，用「模型定时版提示词」；改间隔用 `update_trigger` |
| Claude Code（本机） | `/loop 30m <提示词>`，或者用定时任务 |
| Codex 桌面应用 | 在应用里建一个 Automation（自动化），工作目录选自己的那份克隆。它是**只能定时唤醒模型**的环境（除非另有验证），用「模型定时版提示词」，起始间隔 30 分钟 |
| 其他工具 | 用它自带的计划任务；没有的话，用系统的 cron（macOS / Linux）或任务计划程序（Windows）每 30 分钟运行 `node tools/board.mjs <名字>`，输出里有“待办”时再叫醒 Agent |

没有任何定时功能的 Agent，只能在每次会话开始时跑一遍 board。那样它漏掉的事，由其他 Agent 在 PR 上留言催（`handoff:any` 会让别人也看到），最后才是房主。

## 模型定时版提示词

只能定时唤醒模型的环境用这段（把 `<名字>` 换成这个 Agent 的名字）。脚本过滤的环境用下一节的通用提示词：

```
检查隔壁仓库有没有需要你处理的事，并按项目状态调整你自己的检查间隔。

1. 进入你自己的克隆（不要用别人的目录），git fetch origin main。
2. 运行 node tools/board.mjs <名字> --next-check（没有待办也要运行）。输出是一个数字才算有效：30 是活跃，1440 是休眠或暂停。出错（退出码 20 或没有数字）这一轮不要改定时，只记本地日志，不要评论。
3. 数字有效，并且和你现在的定时间隔不同，就把你的定时改成这个数字；你的工具改不了自己的定时，就保持原样并在 docs/agents/capabilities.md 里写明。
4. 运行 node tools/board.mjs <名字> --quiet。没有输出就结束；退出码 10 才继续，按输出的顺序处理（评审、修改、回复新评论、合并、issue，规则见 AGENTS.md），处理完再运行一遍，直到没有输出。
遇到只有房主能做的事，按 AGENTS.md 打 needs-human 并说明原因，不要自己拍板。
```

## 通用提示词（脚本过滤的环境）

把 `<名字>` 换成这个 Agent 的名字：

```
检查隔壁仓库有没有需要你处理的事。

1. 进入你自己的克隆（不要用别人的目录），git fetch origin main。
2. 运行 node tools/board.mjs <名字> --quiet。没有任何输出就结束，什么也不做；退出码 20 是出错，只记本地日志，不要评论。
3. 有输出才继续，按输出的顺序处理：
   - “待你评审”：读 AGENTS.md「评审」，按格式发评审评论，通过的话打 reviewed:<名字>。
   - “等你修改”：按评审意见修改，推送，回复每一条，改回 ready-for-review。
   - “有人在你的 PR 上留了新评论”：读一读，需要的话回复或修改。
   - “可以由你合并”：确认三项检查全绿，再合并。
   - issue：按 AGENTS.md 的任务协议处理。
4. 处理完再运行一遍 board（--quiet），直到没有输出。
遇到只有房主能做的事，按 AGENTS.md 打 needs-human 并说明原因，不要自己拍板。
```

## 注意

- 同一台电脑上的多个 Agent 各用各的克隆，各自设置自己的名字，不要用 `--global`。
- 活跃时检查频率不要低于 15 分钟，GitHub 接口有限流。
- 评审和合并都不是“看一眼”的事。board 只告诉你有事，评审要按 AGENTS.md 老老实实读改动、跑检查。
